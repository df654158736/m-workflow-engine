# 错误处理策略指南

## on_error 三种策略

| 策略 | 含义 | 适用场景 |
|------|------|---------|
| **FAIL** | 节点失败 → 整个工作流终止 | 关键路径节点（审批、核心计算）|
| **SKIP** | 节点失败 → 跳过继续执行下游 | 非关键的通知、日志、可选增强 |
| **RETRY** | 节点失败 → 自动重试 | 网络调用、外部 API、数据查询 |

## 选择决策树

```
节点失败后，工作流还有意义吗？
├── 没意义（核心数据/决策依赖此节点）→ FAIL
└── 有意义（辅助功能，可降级）
    ├── 重试可能解决？（网络抖动/临时故障）→ RETRY
    └── 重试也没用？（配置错/逻辑错）→ SKIP
```

## 各节点类型默认建议

| 节点类型 | 建议 on_error | 原因 |
|---------|--------------|------|
| FlinkSQL | RETRY | 数据源可能临时不可用 |
| LLM | RETRY | API 偶尔超时 |
| Tool | FAIL | 写操作失败需要人工介入 |
| Function | FAIL | 计算错误通常是逻辑问题 |
| Condition | FAIL | 条件判断不应失败 |
| Approval | FAIL | 审批是强制流程 |
| Sandbox | SKIP | 用户代码出错不应阻塞主流程 |

## 反模式

- ❌ 所有节点都设 RETRY（掩盖真正的问题）
- ❌ 写操作（Tool）设 SKIP（数据不一致风险）
- ❌ Approval 设 SKIP（绕过审批 = 安全风险）
- ❌ RETRY 没有限制次数（应结合 max_retries 使用）
