# 错误处理策略指南

## on_error 三种策略（OnError 枚举）

| 策略 | 含义 | 适用场景 |
|------|------|---------|
| **FAIL** | 节点失败 → 整个工作流终止 | 关键路径（审批、核心计算、危险操作） |
| **SKIP** | 节点失败 → 跳过继续下游 | 非关键（通知、日志、可选增强） |
| **RETRY** | 节点失败 → 自动重试 | 临时故障（网络抖动、API 超时） |

## 选择决策树

```
节点失败后，工作流还有意义吗？
├── 没意义（核心数据/决策依赖此节点）→ FAIL
└── 有意义（辅助功能，可降级）
    ├── 重试可能解决？→ RETRY
    └── 重试也没用？→ SKIP
```

## 各节点类型默认建议

| 节点类型 | 建议 on_error | 原因 | 重试成本 |
|---------|--------------|------|---------|
| FlinkSQL | **RETRY** | 数据源可能临时不可用 | 5s + ¥0.005/次 |
| LLM | **RETRY** | API 偶尔超时 | 8s + ¥0.02/次 |
| Tool（写操作） | **FAIL** | 重试可能重复写入 | — |
| Tool（通知） | **SKIP** | 通知失败不应阻塞 | — |
| Function | **FAIL** | 计算错通常是逻辑问题 | — |
| Condition | **FAIL** | expression 有错不应重试 | — |
| Approval | **FAIL** | 审批绝不能跳过 | — |
| Sandbox | **SKIP** | 用户代码出错不应阻塞 | — |

## 反模式

- ❌ Condition/Approval 设 RETRY（永远无意义）
- ❌ 写操作设 SKIP（用户以为执行了实际没有）
- ❌ Approval 设 SKIP（绕过审批 = 安全风险）
- ❌ LLM RETRY 不限次数（无限重试耗尽 token 预算）
