# Code Review — 交付质量审查

以**负责任的工程师**身份，对本次交付进行全面 Review。

---

## Review 维度

### 1. 功能正确性（Correctness）

- 需求是否完整实现？是否有遗漏的边界条件？
- 数据流是否正确？API 调用链是否完整？
- 错误处理是否合理？异常路径是否覆盖？
- 是否有明显的 Bug 或逻辑缺陷？
- 测试覆盖是否足够？单元测试 + 接口测试是否覆盖核心路径？

### 2. 开发边界合规

- 新增 REST API 是否放对了位置？（按 CLAUDE.md 开发边界规则判断）
- 前后端职责是否清晰？前端是否包含了不该有的业务逻辑？
- 是否违反了 CLAUDE.md 技术红线中的任何一条？

### 3. 前后端契约一致性（Contract Alignment）

- API 请求/响应类型定义（TypeScript types）是否与后端 Pydantic model 对齐？
- API 路径、HTTP method、状态码是否前后端一致？
- 如果没有 API 变更则跳过此维度。

### 4. 接入体验与代码质量（Developer Experience）

- API 设计是否直观？命名是否清晰一致？
- 是否遵循项目既有的代码风格和分层约定？
- 新增的 API 是否有 OpenAPI/Swagger 文档？
- 代码是否易于理解？复杂逻辑是否有必要注释？
- 日志是否足够排查问题？关键路径是否有 log？
- 配置是否外部化？是否有硬编码的值？

### 5. 演进成本（Evolvability）

- 架构设计是否支持未来扩展？是否过度设计？
- 是否引入了不必要的耦合？依赖方向是否正确？
- 是否有重复代码可以抽象？是否有过早抽象？
- 是否影响其他模块？blast radius 是否可控？

---

## Review 流程

1. **确定 Review 范围** — 基于 `git diff` 确认实际变更文件
2. **分类变更文件** — 按模块归类（backend API / frontend component / 测试 / 配置）
3. **逐文件审查** — 按上述 5 个维度逐一检查每个变更文件
4. **契约对齐检查** — 如涉及 API 变更，验证 backend Pydantic model ↔ frontend TypeScript types 一致性
5. **开发边界检查** — 逐条过 CLAUDE.md 技术红线
6. **对照设计文档** — 如果有关联的设计文档（`docs/design/` 或 `docs/specs/`），验证实现与设计是否一致

## 输出格式

### 问题清单（按优先级排序）

| 优先级 | 类别 | 文件 | 问题描述 | 建议修复方案 |
|--------|------|------|---------|-------------|
| P0-阻塞 | | | | |
| P1-重要 | | | | |
| P2-建议 | | | | |
| P3-优化 | | | | |

> - **P0-阻塞**：必须修复才能交付 — 功能不正确、安全问题、技术红线违反
> - **P1-重要**：强烈建议修复 — 契约不对齐、测试缺失、关键日志缺失
> - **P2-建议**：建议改进 — 命名不一致、注释不足、文档缺失
> - **P3-优化**：可选优化 — 长期演进方向、抽象建议

### 亮点（值得保持的好实践）

列出本次交付中做得好的地方，鼓励团队保持。

### 交付结论

- **可以交付** — 无 P0/P1 问题，代码质量达标
- **修复后交付** — 存在 P1 问题需修复，列出具体修复项
- **需要重新设计** — 存在 P0 问题或架构性问题，需要返工
